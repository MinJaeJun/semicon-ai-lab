# CellHealth — 스토리지 필드 헬스 자연어 질의 + 마모 예측

출하된 모바일 스토리지 10만 대의 텔레메트리 20만 행에 대해,
**자연어로 물으면 정확한 숫자로 답하는 엔진**과 **마모 위험 예측 모델**을 만든다.

```bash
python generate.py   # 데이터 생성 + 검증
python analyze.py    # 질의 엔진 실행 → 마모 모델 학습
```

## 문제 1 — 대용량 데이터에 자연어로 묻기

분석이 필요할 때마다 파이썬 코드를 새로 쓰는 상황을 없애고 싶다.
그런데 데이터를 LLM 에 통째로 넘기면 **숫자가 틀린다.**
품질 데이터에서 숫자가 틀리면 도구로서 가치가 0 이다.

### 접근: LLM 을 부르지 않는다

컬럼 사전과 규칙 파서로 질문을 실행 계획으로 바꾸고, 집계는 pandas 가 한다.

```
질문 → [집계함수 | 그룹축 | 필터조건 | 지표컬럼] → pandas 실행 → 결과 + 근거
```

답변에는 항상 **사용한 컬럼, 적용한 필터, 스캔/매칭 행 수**를 붙인다.
사람이 검증할 수 있어야 하기 때문이다.

### 결과: 7/7 해석 성공

| 질문 | 결과 |
|---|---|
| 벤더별 평균 PE 사이클은? | HYX 467.1 / SMS 437.4 / MCR 375.2 |
| 제품군별 uecc 평균은? | eMMC5.1 0.0256 / UFS2.2 0.0252 / UFS3.1 0.0250 |
| pe_cycle 이 2000 이상인 디바이스 개수는? | 1,518 |
| 소모율이 0.7 이상인 디바이스의 평균 rtbb 는? | 3.71 |
| 벤더별 잔여 수명 중앙값은? | 세 벤더 모두 87 |
| 온도 70 이상인 디바이스의 최대 uecc 는? | 58 |
| 회차별 평균 소모율은? | 1차 0.112 → 2차 0.223 |

전체 결과와 실행 계획은 `outputs/query_results.json`.

## 문제 2 — 마모 위험 예측

`uecc > 0` (정정 불가 비트 에러 발생) 여부를 맞춘다. 양성 비율 **0.76%**.
이 정도 불균형에서는 정확도가 무의미하므로 **PR-AUC** 로 평가한다.

| 모델 | PR-AUC | ROC-AUC | 상위 2% 정밀도 | Lift |
|---|---:|---:|---:|---:|
| 로지스틱 회귀 | **0.416** | 0.731 | **0.178** | **23.4** |
| Gradient Boosting | 0.393 | 0.719 | 0.172 | 22.6 |

상위 2% 를 골라 정밀 검사하면 **기저율 대비 23배** 농축된다.
출하 10만 대 중 2,000대만 열어봐도 위험 디바이스의 상당수를 잡는다는 뜻이다.

### 마모 무릎 지점

| pe_ratio 구간 | uecc 발생률 |
|---|---:|
| ~0.40 | 0.44% |
| 0.40 ~ 0.55 | 0.40% |
| 0.55 ~ 0.65 | 0.39% |
| 0.65 ~ 0.75 | 0.46 ~ 0.67% |
| **0.75 ~ 0.85** | **8.45%** |
| **0.85 ~ 1.00** | **48.16%** |
| 1.00 초과 | 96.86% |

0.75 를 넘는 순간 **20배**, 0.85 를 넘으면 **100배 이상** 뛴다.
0.75 아래로는 완전히 평평하다. **잔여수명을 선형 외삽하면 안 되는 이유다.**

다만 이 데이터에서 트리 모델이 로지스틱을 이기지는 못했다 (PR-AUC 0.393 vs 0.416).
무릎이 있어도 `pe_ratio` 하나가 위험도를 단조적으로 결정하면 선형 모델도 충분히
순위를 매길 수 있기 때문이다. 무릎이 있다고 자동으로 트리가 이기는 게 아니라는 뜻이고,
확인해 보기 전에는 단정하면 안 된다.

## 데이터

`data/device_health.csv.gz` — 200,000행 × 18열 (10만 대 × 2회차)

같은 `device_uid` 를 두 회차에 걸쳐 추적할 수 있다. 2차 수집 시점에 마모가 실제로
진행돼 있다 (평균 소모율 0.111 → 0.223).

| 컬럼 | 의미 |
|---|---|
| `device_uid` | 디바이스 고유 ID (회차 간 동일) |
| `collect_round` / `collect_date` | 수집 회차 / 일자 |
| `vendor` | 제조사 (HYX / SMS / MCR — 정격 P/E 수명이 다르다) |
| `product_family` | UFS3.1 / UFS2.2 / eMMC5.1 |
| `part_no` / `density_gb` / `fw_version` | 제품 식별 |
| `storage_used_gb` / `storage_util` | 사용 용량 / 사용률 |
| `pe_cycle` | 블록 Program/Erase 반복 횟수 |
| **`pe_ratio`** | **정격 대비 소모율 — 벤더/제품군별 정격이 달라 정규화가 필수** |
| `tbw_gb` | 누적 기록량 |
| `power_on_hours` / `temp_max_c` | 누적 가동 시간 / 최고 온도 |
| `rtbb` | Run Time Bad Block |
| `uecc` | Uncorrectable ECC |
| `health_pct` | 컨트롤러 보고 잔여 수명 |

전체 사전은 `data/column_dictionary.csv`.

## 데이터에 심어둔 성질

1. **비선형 마모** — pe_ratio 0.70 에 무릎. 그 위로 멱함수적 증가(지수 2.1 / 2.6).
2. **정격 차이** — 벤더별 정격 P/E 가 2400~3000, eMMC 는 그 62%.
   `pe_cycle` 원값으로 비교하면 틀린다.
3. **희소 불량** — rtbb>0 2.5%, uecc>0 0.7%. 전체 평균만 보면 아무 일도 없어 보인다.
4. **헤비유저 꼬리** — 사용 강도가 로그정규. 소수가 극단적으로 많이 쓴다.
